# 基本面检索闭环、专题写作与 HTML 报告实施计划

## 目标

在不增加 Worker、队列、外部服务或独立编辑 Agent 的前提下，补齐两类 Specialist 的检索边界与受控闭环，并把最终报告从固定四段摘要升级为专题化正式写作和动态原生 HTML。报告以材料覆盖与论证质量为优先；5,000–8,000 字是材料充分时的通常预期，不设字数硬性拦截，也不以泛化文字凑篇幅。

## 范围

- 纳入：Business / Industry 检索任务卡、最多两轮的检索—读取—改写查询闭环、Evidence 复用与去重、Writer 编排和正文 Schema、机构投研编辑版 HTML、Manifest 升级与测试。
- 不纳入：新增 Agent、增加 Worker、外部数据 Provider、交易指令、买卖评级、收益承诺，或将研报原文/目标价复制进报告。

## 检索闭环设计

新增一个受信、轻量的 Specialist 检索编排脚本（建议模块：`app/fundamental/research_loop.py`）。脚本只串联现有搜索和来源读取能力，不引入新基础设施：

```text
任务卡 → 第 1 轮查询 → 搜索 → 读取候选来源 → 覆盖盘点
                                          ↓
                              未覆盖问题 / 已见 URL / 已得事实
                                          ↓
                           第 2 轮改写查询 → 搜索 → 读取 → 输出研究简报
```

- 循环上限为 2 轮（严格小于 3）。若第一轮覆盖任务卡，立即停止；第二轮结束后，无论是否仍有缺口都输出已有 Evidence 和未解决事项。
- 每一轮必须先检索、再读取选定来源；仅在读取后依据覆盖盘点生成下一轮查询。禁止连续多次搜索后再批量读取。
- 改写输入仅包含角色任务卡、已覆盖事实、未覆盖子问题、已见 URL/内容指纹及上一轮查询；不得注入来源全文或其他 Run 内容。
- 同一 URL/内容在 Run 内只入库一次；不同角色可引用同一 Evidence，但下一轮查询优先寻找未见来源和未覆盖信息，不因“已有来源”而禁止必要的交叉验证。
- 脚本产出可审计的轮次记录：角色、任务卡 ID、查询词、搜索结果 URL、读取 Evidence、已覆盖/未覆盖问题和停止原因。它作为研究产物的元数据或独立轻量 Artifact，不向 Writer 注入完整检索过程。

## 角色任务卡与查询改写规则

Lead 只给出研究范围和高优先级问题；脚本将其转换为带角色边界的任务卡，而非让两个 Specialist 临场自由生成相似关键词。

| 角色 | 研究对象 | 查询改写原则 | 明确排除 |
| --- | --- | --- | --- |
| Business | 公司本身 | 使用公司名、项目/矿山/产品、产能、投放、客户、渠道、资产、并购、海外运营和执行风险等组合词；优先公司披露与项目资料。 | 全球供需、商品大盘、同业成本曲线等纯外部行业问题。 |
| Industry | 公司所暴露的外部产业与区域 | 从公司资料和 Lead 范围提取矿种、地区与下游暴露；以矿种/区域/产业链为主语，组合供需、库存、价格、成本曲线、可比矿企、资源国政策、技术替代和周期等词。公司名只可作为暴露限定词，不能作为主检索对象。 | 公司半年报、公司产量、公司项目并购等应由 Business 完成的公司事件。 |

以紫金矿业为例，Industry 的第二轮词应向“2026—2027 全球铜矿供给增量与矿山扰动”“黄金供需与央行购金”“碳酸锂供给、库存、下游需求及价格”“刚果（金）/塞尔维亚矿业政策”等外部专题收敛，而非改写为另一组“紫金矿业业绩、产量、Allied Gold”。

## Writer 与报告设计

- 将当前固定的 `business`、`industry`、`financial`、`valuation` 四个一句话摘要替换为可变 `report_composition`：3–6 个专题章节、叙事顺序、章节目标、获准 Evidence/Assumption、以及表格/图表/时间线意图。
- Lead Synthesis 只决定材料准入、主线和优先专题；Writer Planning 决定报告怎么讲；Fundamental Writer 写出连续的专题正文。
- 每个专题正文遵循“核心判断—事实与数据—解释及影响—后续观察”的研报节奏，但不机械要求每段或每条 finding 都有新增 Evidence。材料不足时缩短该专题并放入独立“优化建议”，不得用空泛结论补字数。
- 将参考研报仅用作专题拆解、结论先行、图表支撑与段落节奏的风格参照；不得复用其原文、评级、目标价或收益预测。
- 原生 HTML 根据 `report_composition` 动态生成机构投研编辑版式：专题页、可变表格/时间线/Canvas 图表、清晰的数字排版和独立“优化建议”板块；不再使用固定 Hero、KPI 卡片和四章节模板。

## 实施步骤

1. 为角色任务卡、检索轮次审计记录、`report_composition` 和专题正文定义 Schema，并明确 Evidence/Assumption 引用校验。
2. 为 Business / Industry 增加确定性的任务卡与查询改写模板，覆盖公司镜头与外部产业镜头的边界。
3. 实现最多两轮的轻量 Specialist 检索编排脚本，强制“搜索→读取→覆盖盘点→必要时改写”的时序、早停和预算处理。
4. 调整来源缓存与 Evidence 写入，使 URL/内容去重、跨角色引用和轮次审计可共存。
5. 改造 Workflow，使 Business、Industry 使用编排脚本生成研究简报；Deep Research 后续改为 1–3 个专题深化任务时复用同一闭环协议。
6. 调整 Lead Synthesis、Writer Planning 与 Fundamental Writer 的上下文、Prompt 和输出 Schema，赋予 Writer 正文论证与编排能力，同时保持零工具和最终角色的交易限制。
7. 重写报告生成器和共享样式令牌，按专题编排生成离线可用的原生 HTML/Canvas 报告。
8. 更新 Manifest 依赖、旧 Run 升级与恢复逻辑，确保最早从受影响的任务卡/研究节点失效重建，避免旧摘要混入新报告。
9. 先新增失败测试，覆盖角色查询边界、轮次上限、读取后改写、早停、URL/内容复用、专题正文、动态 HTML、引用合法性、优化建议隔离和旧 Run 升级。
10. 完成实现后运行全量 Python 测试、Pi Bridge 测试与构建，并进行独立 Web + Worker Mock 端到端验收；Live 凭证可用时，额外检查真实检索词和 Writer 成品质量。

## 风险与验收边界

- 若第一轮已覆盖任务卡，第二轮不得为了凑轮次继续搜索；若来源不足，必须留下未覆盖事项而不是报错或伪造结论。
- `sources` 继续仅作排序偏好，不成为 Provider 硬权限。
- Writer 的最终 Prompt 继续承担交易指令和收益承诺限制；不增加来源阶段的硬性内容阻断。
- 验收时以查询轮次审计验证 Industry 未以公司事件为主检索对象、Business 未以宏观行业问题为主检索对象，并确认任一 Specialist 的循环次数不超过 2。
